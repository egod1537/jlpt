# Refactoring Guidelines

이 프로젝트에서 "리팩토링" 요청을 받으면 이 문서를 먼저 기준으로 삼는다.

## React Component Policy

- React 컴포넌트는 클래스 컴포넌트를 기본 형태로 둔다.
- 기존 함수형 React 컴포넌트는 클래스 컴포넌트로 전환한다.
- 특히 아래 중 하나라도 해당하면 반드시 클래스 컴포넌트로 작성한다.
  - 상태 값이 3개 이상이다.
  - React hook을 사용한다.
  - 생명주기, 저장소 동기화, 복잡한 이벤트 흐름이 있다.
- 상태가 없는 반복 UI는 `PureComponent`를 우선 사용한다.
- 컴포넌트가 아닌 순수 유틸 함수, 타입 가드, 포맷터, 데이터 빌더는 함수로 유지한다.
- hook을 새로 추가하지 않는다. 같은 동작은 클래스 state, lifecycle method, 서비스 객체, 순수 함수로 표현한다.

## File Size And Module Boundaries

- 한 소스 파일은 작고 명확한 책임만 가져야 한다.
- 컴포넌트 파일이 길어지면 아래 순서로 분리한다.
  - 순수 계산 로직은 `.ts` 헬퍼 모듈로 이동한다.
  - 반복되는 UI 조각은 별도 클래스 컴포넌트로 이동한다.
  - 데이터 준비, 저장소 접근, 세션 제어는 서비스나 유틸 계층으로 이동한다.
- 큰 파일을 그대로 두고 내부 함수만 늘리는 방식은 피한다.
- 파일 하나가 200줄을 넘기 시작하면 분리 가능성을 검토한다.
- 300줄 이상인 React 컴포넌트 파일은 리팩토링 대상이다.

## Refactoring Workflow

1. `src/**/*.tsx`에서 함수형 컴포넌트와 hook 사용 여부를 확인한다.
2. 클래스 컴포넌트 전환이 필요한 컴포넌트부터 처리한다.
3. 200줄 이상 파일과 책임이 섞인 파일을 찾아 순수 로직, UI, 서비스 책임으로 나눈다.
4. 기존 props/state 계약과 화면 동작을 보존한다.
5. unrelated 변경, 대규모 스타일 변경, 데이터 변경은 리팩토링에 포함하지 않는다.
6. 작업 후 `npm run typecheck`를 실행한다.
7. 타입체크가 통과하면 가능하면 `npm run build`도 실행한다.

## Current Codebase Notes

- 컴포넌트 export는 클래스 컴포넌트 또는 `PureComponent` 형태를 유지한다.
- 퀴즈 세션처럼 상태와 이벤트가 많은 화면은 컨트롤러/뷰모델/렌더 컴포넌트로 나누어 파일 크기를 낮춘다.
- 새 React 컴포넌트를 추가할 때도 이 문서의 클래스 컴포넌트 기준을 따른다.
